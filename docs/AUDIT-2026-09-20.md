# Full Repo Audit — 2026-09-20

Requested: a comprehensive, honest audit and conclusion covering (1) missing/wrong/stale inline code documentation, (2) gaps in implementation, (3) missing tests, (4) "boss files" (very large, human-unreadable files), (5) stub/placeholder code, (6) outstanding TODOs, (7) missing features, (8) unlinked/orphaned features, and (9) e2e-untested features — against a stated definition of done: 100% test coverage, no gaps/stubs/placeholders, 100% correct in-code documentation, 100% e2e tested, 100% mutation tested, no code warnings, no type issues.

This document reports what is actually true of the code today, verified directly (ground-truth commands run fresh, imports traced, comments checked against the code they describe) rather than taken from milestone docs' own "implemented cleanly" claims. Four independent passes fed this report: one direct ground-truth pass (build/lint/test/grep), and three research passes (test-coverage cross-referencing, documentation staleness, feature reachability/orphan tracing).

**Bottom line up front: the codebase is in genuinely good shape for a project of this size — types, lint, and Go build/vet are 100% clean, and there is no dishonesty in the code (no fake success, no silently-swallowed errors found). But measured strictly against the stated definition of done, it does not meet it, on five specific, concrete axes: test coverage, e2e testing, mutation testing, one architecture-rule violation, and a handful of stale/missing documentation spots.** None of this is hidden — nearly every gap below was already self-disclosed somewhere in the project's own docs (most commonly as "stays manual, no headless browser in this environment"). What this audit adds is verification that those self-reports are accurate, a few they missed, and one place they're wrong.

## 1. Missing, wrong, or stale in-code documentation

The project's own convention (CLAUDE.md) is "default to no comments; only comment non-obvious WHY" — so the bar here isn't JSDoc-on-everything, it's: are the comments that exist accurate, and is genuinely risky code silent when it shouldn't be?

**Confirmed stale/inaccurate comments (2, both minor):**
- `apps/web/src/core/state/actions.ts:19-21` — `ARCHETYPE_SEEDS`'s comment attributes its export to being read by `BalanceSimulator.ts`; in reality only `BalanceSimulator.test.ts` imports it (the production module takes an injected seed param instead). Misnames which file needs it.
- `apps/web/src/world/WorldScene.ts:1279` — `reduceStress(0); // placeholder — community effect captured in trust` is a confirmed true no-op call (`Math.max(0, x-0)`); the comment explains *why* it does nothing but not why the dead call wasn't just deleted.

Everything else specifically chased down (several `RegionScene.ts`/`RegionData.ts`/`WorldScene.ts` "placeholder" comments flagged by an initial grep) turned out to be accurate on close reading — either genuinely historical (documenting a since-renamed function) or referring to something narrower than "placeholder" first suggested.

**Real documentation gap — security/trust-boundary code is silent:**
- `apps/web/src/core/kernel/PluginSandbox.ts` (iframe `allow-scripts`-without-`allow-same-origin` sandboxing + `postMessage` nonce protocol) — **zero comments**, no explanation of why this is the actual security boundary or why a wildcard `postMessage` target is safe here.
- `apps/web/src/core/kernel/SandboxedPluginRuntime.ts` (341 lines) — same, zero comments on the sandbox boundary it enforces.
- `apps/web/src/core/kernel/PluginRegistry.ts` (416 lines) — zero comments despite real security decisions living in it: an `ALLOWED_PERMISSIONS` whitelist, `isAllowedRemoteUrl()` (an explicit same-origin/https/localhost tradeoff with SSRF implications), SHA-256 bundle-hash verification, and a `trusted`/`review-needed` quarantine flag — none of these choices are explained anywhere.
- `apps/api/internal/middleware/auth.go` and `apps/api/internal/auth/{handler,service,token}.go` — the entire JWT bearer-token gate protecting `/api/v1/save` has zero comments in the actual sign/verify code.
- `apps/api/internal/plugins/register.go` — has a genuinely good top-of-file package doc, but `runtimeLoader.load()` (loads arbitrary `.so` files via `goplugin.Open` — real native code execution with full process privileges) has no comment flagging that this server-side plugin path is *unsandboxed*, unlike its web-side counterpart.

**Confirmed CLAUDE.md architecture-rule violation (real, current, not fixed by a later milestone):**
CLAUDE.md's Critical Architecture Rule states "Game logic must never reference sprite filenames, color hex codes, or skin-specific assets" — skins should resolve all visuals via `skin.manifest.json`. This is violated in exactly three files:
- `apps/web/src/world/WorldScene.ts` — `updateWorldDressing()`/`renderOutdoorDressing()` hardcode `{w, h, color: 0x...}` tables directly (e.g. `PROP_BOARDED_WINDOW: {w:12, h:10, color:0x5a4a3a}`), not resolved through any skin manifest.
- `apps/web/src/world/InteriorScene.ts` and `apps/web/src/world/InteractionPrompt.ts` — same pattern.
- Grep counts: 48 CSS-hex-string literals and 69 Phaser `0x`-numeric color literals across these three files. **Zero** hits in `apps/web/src/core/simulation/*.ts` — the violation is confined to the `world/` rendering layer, not spread into simulation logic. This was already flagged as "a pre-existing gap, not something [a later epic] caused" in an earlier planning pass — confirmed still true and still unfixed.

**Stale cross-references found and fixed this session** (outside the code, in docs): three `docs/planning/*.md` files and one archived index doc had relative links (`../stories/EPIC-XX`, `../tasks/MXX`) pointing at paths that no longer exist after today's archiving — including one pre-existing broken link from the 2026-09-15 archiving pass (`docs/planning/00-MASTER-INDEX-AND-DESIGN-BIBLE.md` linking `../tasks/M20-...` when M20 had already been archived). All fixed as part of this close-out (see below).

## 3. Missing tests (the largest concrete gap)

A naive "does this file have a same-directory `.test.ts`" check is misleading in this repo (some tests live in a different directory than their source — e.g. `core/simulation/WorldQuests.ts` is tested by `core/state/WorldQuests.test.ts`). A verified pass (checking real imports, and excluding files only reached via `vi.mock`, which never executes the real code) found:

**apps/web — genuinely 0% covered, high-risk (21 files):**
- The entire plugin-sandboxing kernel: `PluginSandbox.ts`, `SandboxedPluginRuntime.ts`, `PluginRegistry.ts` — the same security-relevant code flagged as undocumented above is also completely untested.
- Core game loop: `WorldScene.ts` (1,629 lines — see §4), `InteriorScene.ts`, `RegionScene.ts` (excluded from unit testing by established convention — they `import Phaser` at module scope — but this means the actual game loop has no direct automated coverage at all, only the pure logic modules it calls into).
- `CollisionSystem.ts` (0 hits at all).
- `InputManager.ts` — only ever `vi.mock`'d by other tests; its real code never executes under test.
- 17 of the ~20 UI Modal files (`CraftingModal`, `HousingModal`, `RetailModal`, `FurnitureEditorModal`, `ProximityVisitModal`, `SocialHubModal`, `WorkModal`, `ShopModal`, `TerminalModal`, `DistrictBuilderModal`, `CivicDirectoryModal`, `QuestModal`, `WorldMapModal`, `GeoPreviewModal`, `PluginManagerModal`, `AuthOverlay`, `FriendDistrictViewer`) — 0% real coverage.
- All 12 `api/endpoints/*.ts` fetch wrappers — 0% coverage collectively (individually thin/low-risk, but the whole HTTP boundary layer is untested).
- 4 entity classes (`PedestrianEntity`, `ScrapsEntity`, `PigeonEntity`, `PlayerEntity`) — 0 hits.

**packages/* — genuine gaps, not low-risk:**
- All 5 minigame packages (`minigame-courier-rush`, `-kitchen-rush`, `-solidarity-line`, `-tenant-match`, `-tool-workshop`) — **0 test files each**, 390–460 lines of real gameplay-loop code per package.
- All 4 hi-fi skin renderer packages (`skin-diorama-glow`, `-flat-vector`, `-neon-city`, `-painterly-depth`) — **0 test files each**, 229–343 lines of real rendering logic per package.
- The 4 mesh/transport/civic plugin packages, by contrast, are well tested (3–5 test files each).

**apps/api (Go) — 7 of 17 packages have no test files.** Per-package risk verdict:
- `internal/middleware` (auth.go, cors.go, recover.go) — **real gap, highest priority.** This is the `RequireAuth` bearer-token gate for the entire API, real CORS preflight branching, and the server-wide crash-recovery handler. Completely untested.
- `internal/config` — **real gap.** Contains the security-critical fail-fast checks CLAUDE.md itself mandates (`JWT_SECRET`/`GAME_SESSION_SECRET` ≥32 bytes). A boundary-condition bug here would silently weaken secrets.
- `internal/plugins` — **real gap.** Non-trivial: concurrent `.so` file discovery, mutex-guarded dedup, a polling goroutine, dynamic symbol lookup — genuine bug-hiding surface, untested.
- `internal/theme` — low-to-moderate risk (simple filter/merge logic).
- `cmd/server`, `internal/db`, `internal/gamedata` — low risk, thin glue/wiring code with little branching.

**Corrections to the naive check** (files that ARE tested, just not colocated): `core/simulation/WorldQuests.ts`, `core/kernel/HostPlatformAPI.ts`, `skins/SkinInterface.ts`, `ui/broadsheetHTML.ts`, and 6 fixture files loaded via dynamic `import()` inside loader tests — all confirmed genuinely covered.

There is no coverage-threshold enforcement anywhere (`vitest.config.ts` has no `coverage` block; no `test:coverage` script exists), so this gap can silently widen with every future change.

## 9. e2e-untested features

This is close to "every interactive feature in the game," and the project has been honest about it every time: **every single visual/interaction milestone from M21 through M54** (17+ milestones) explicitly records its actual interactive round-trip — walk somewhere, open a modal, click through, confirm the result — as "stays manual, no headless browser available in this environment." Verification in every one of those milestones reduces to: `tsc` clean, `vitest` clean on the pure-logic modules, and an HTTP-200 fetch check against the dev server for changed files. That confirms the code *compiles and serves*, not that any interaction actually works end-to-end as played.

Concretely, this means there is no automated evidence in this repository that any of the following have ever been driven end-to-end: character creation, world movement, dialogue trees, crisis resolution, building entry/exit, crafting, buying/selling, housing/furniture editing, quest pickup/completion, minigame play, skin switching, or mesh-based proximity visiting. This is the single largest, most consistent gap against the stated definition of done, and it's structural — no Playwright/Cypress/Puppeteer exists in the repo to close it (confirmed in the Verification Results table above), not a matter of a few missing test files.

## Conclusion

**Archiving/cleanup (this session's first ask): done.** All of M1–M54 is `[x] Implemented` or `[~] Superseded`; every complete story epic and task doc is now under `docs/archive/` except M33/M36/M37 (kept in `docs/tasks/` on purpose, as superseded audit records — their stale "Planned" headers are now fixed) and TD1 (genuinely blocked tech debt, correctly still tracked). `docs/TASK-STATUS.md` shrank from 596 to ~150 lines by removing a 430-line legacy duplicate section and condensing 27 near-duplicate Status Log entries into 5 grouped summaries, with zero loss of the underlying facts (all preserved in the archived docs themselves). Several stale cross-reference links (including one left over from the 2026-09-15 pass) were found and fixed.

**Against the stated definition of done, the codebase does not meet it — but the gap is honest, narrow, and already mostly self-documented, not hidden rot:**
1. **Types/lint/build are already at 100%** — tsc, oxlint, `go build`, `go vet` are all clean today.
2. **Test coverage is well short of 100%**, concentrated in exactly the highest-risk code: the plugin-sandboxing kernel, the Go auth middleware, and nearly every player-facing UI modal. No coverage tooling exists to even measure the real percentage.
3. **e2e testing is at 0%** structurally — no framework installed, and this has been true (and disclosed) since the project's early milestones.
4. **Mutation testing is at 0%** — no tool installed, never attempted.
5. **Documentation is very good but not 100%**: two stale comments, one real category of undocumented security-sensitive code (the plugin sandbox + Go auth layer), and one confirmed, unfixed CLAUDE.md architecture-rule violation (hardcoded colors in three `world/` files).
6. **No hidden stubs or dishonest TODOs** — the few real placeholders that exist are all self-aware, commented, and consistent with what the task docs already say.
7. **One dead-but-tested file** (`BuildingInteriorLoader.ts`) and one genuinely oversized file (`WorldScene.ts`, 1,629 lines, also the least-tested and only architecture-rule-violating file in the repo) are the two concrete cleanup targets, if a future pass wants one clear place to start.

If the next phase of work is "close the gap to the stated definition of done," the highest-leverage order is: (a) add an e2e framework and cover the core loops nothing else can verify, (b) test the plugin-sandbox/auth code specifically (small file count, highest risk), (c) add `vitest` coverage-threshold enforcement so this doesn't silently regress again, (d) route `WorldScene.ts`'s hardcoded dressing colors through the skin manifest to close the one architecture violation, and (e) only then chase the long tail of untested UI modals and mutation testing. That prioritization, not a blanket "test everything," is this audit's one recommendation beyond reporting what's true.
