# 21 — Open World, Deep Crafting & Living Identity: A Vision for District: Common Ground's Next Era

## Origin

The user, following EPIC-31 (World/HUD/Progression) and EPIC-32 (Home & Housing, planned but not yet built), asked for something much larger than another milestone (2026-09-19, paraphrased close to verbatim):

> Think the interior build and the whole building system a bit like Minecraft — it should be possible to find any kind of material and stuff that can be reused to upcycle and build things, for building interiors but also things like building a bike, which can be sold later. Make the whole concept of upcycling and crafting from found things much broader, for many more things. Make "buildings" — metal workshops, wood workshops, a Baumarkt (hardware store), supermarket, and others — that can really be *entered*: on the worldmap they have a roof, and entering loads a new internal space with people in it. These could be small pieces, like plugins, so the worldmap and every element and building can be developed very fine-grained. Think everything as it would really be to build and create it in real life — buildings, toys, tools, all needing something like a "cookbook" you can earn or find in the world. Think the main world much more as a world with regions, like a real open-world game — World of Warcraft. The start of the game should really be like being born from a random family — you can adjust the name and maybe the sex, but it can also be diverse. Think this as a real game with a lot of development and many ways to play — for example, computers can be built in-game too. Do not code yet — comprehensively write down all these ideas as vision documents, from which epics, stories, and tasks can be created. Also plan the move from simple 2D pixel graphics to real hi-fidelity graphics, like the newer Rayman games.

This document is that write-down: a single, deliberately broad vision, planned against the real current codebase (not written in a vacuum), that the five new epics under `docs/stories/` and their task docs under `docs/tasks/` are cut from.

## Grounding — what already exists to build on

Before proposing anything new, here is what the live code already gives this vision to work with (all confirmed by direct reading, not inference):

- **A proven "fine-grained plugin" pattern already exists, twice.** M14/M29 built a real microkernel minigame-plugin system (`MinigameLoader`, dynamically-`import()`ed ESM bundles under `apps/web/public/plugins/`) and M30 built a parallel `SkinRenderer` plugin system the same way, each shipping as an independent `packages/*` workspace package with its own build step. The user's "small pieces, like plugins" instinct for buildings is not a new idea for this codebase — it is the established way this project already ships fine-grained, independently developed content. This vision leans on that precedent directly rather than inventing a new mechanism.
- **The skin/token architecture already forces "no hardcoded visuals in game logic."** `SkinInterface.ts`/`ThemeManager.ts`'s `EntityToken`-and-`skin.manifest.json` resolution (CLAUDE.md's Critical Architecture Rule) is exactly the pattern a materials/crafting/character-appearance system needs: abstract tokens in state, resolved to actual art only at render time.
- **`GameState` currently has no inventory, no items, no housing, no family, and character creation is a single upfront pick of one of 3 fixed archetypes** (`useGameStore.ts`, `CharacterSelect.ts` — confirmed by direct read). There is real room here; nothing in this vision has to fight existing state shape, only extend it.
- **The map is one deterministic, hand-authored 64×80 tile grid** (`MapData.ts`, M32) covering a single town — real biome variety exists within it (trees/water/paths as of M32) but there is exactly one region, ever.
- **Every visual layer in the game today is 100% programmatic** — canvas-drawn rectangles, gradients, and one dithered-noise pattern, confirmed end-to-end by M30's audit (even the "hi-fi" skins are procedural techniques, not art files). There are zero image/sprite assets anywhere in the render path.
- **The economy, crisis, and quest systems already have clean, reusable "apply a tradeoff" hooks** (`applyDailyTick()`, `CrisisEngine.ts`'s `consequences` shape, `IrlQuestSystem`) that a crafting/materials economy and a region-travel system can both plug into rather than needing parallel new plumbing.

## The Six Pillars

1. **Crafting, Materials & Upcycling** (Minecraft-inspired) — find things, learn recipes, make things, use or sell them.
2. **Buildings as Plugins** — every enterable structure (workshop, store, home) is a real, independently-developable interior "level," loaded on entry.
3. **Open World Regions** (WoW-inspired) — the game grows from one town into a world of connected regions, each with its own materials, buildings, and people.
4. **Character Origin, Family & Identity** — the game begins with being born, not with picking a card; name, gender, and background are the player's to shape.
5. **Hi-Fidelity Art Direction** (Rayman-inspired) — a deliberate, phased move from programmatic primitives toward hand-crafted visual richness.
6. **The Hub-and-Plugin Universe & Proximity Multiplayer** — added per a direct follow-up from the user: the base game is a lean "hub" that every other pillar docks onto as a plugin, eventually including other real players' plugin-hosted spaces, visited over the existing mesh-networking system when nearby and invited in.

Each pillar becomes its own epic (`EPIC-33` through `EPIC-38`) with its own milestones, because each is an architecturally distinct body of work with its own risks — exactly the reasoning EPIC-31 already used to split itself into 5 milestones rather than one. They are written together here because they reinforce each other constantly (see "Cross-Cutting Systems" below); they will not all be *built* at once, and Pillar 6 in particular is sequenced last and kept small on purpose (see its own section below).

## Pillar 1 — Crafting, Materials & Upcycling

**The core loop:** forage or scavenge → hold raw/reclaimed materials in an inventory → learn or find a recipe (a "cookbook" entry) → craft or upcycle an item at an appropriate station → use it, wear it, ride it, furnish a home with it, or sell it.

**Materials, not currency-with-extra-steps.** Today the only resource is cash. This pillar adds a second resource layer — physical materials — sourced three ways: scavenging fixed, deterministic pickup points scattered through the world (an abandoned bike frame behind the Utility Station, scrap sheet metal near the Solar Quarter, reclaimed lumber stacked outside a workshop — hand-placed, like `OutdoorDressing.ts`'s prop list, never randomly spawned); buying raw stock at the new retail buildings (Pillar 2's Baumarkt/supermarket); and salvaging existing world objects (e.g. breaking down an old crisis-damaged structure for parts, tying materials back into the existing crisis-consequence system).

**The base of the material taxonomy is genuinely raw and natural, not just urban scrap.** Refined per a direct follow-up from the user: the foundation should be real, elemental materials people actually gather in the world — **wood, stone, iron (ore/ingot), coal, gum/resin, wool, cotton, leather, mushrooms** — the kind of thing a forest, a quarry, a farm, or a mine would actually produce. Urban-salvage materials (scrap metal, glass, rubber, electronic components, reclaimed lumber) sit *above* this raw layer as a second, complementary sourcing path — a found bike frame is a shortcut to material an upcycler didn't have to smelt or forge themselves, while iron ore has to go through a smithing step first. Both coexist deliberately: raw-material gathering gives [Pillar 3](#pillar-3--open-world-regions-beyond-the-district)'s new regions (a forest yields wood/mushrooms, a quarry/industrial region yields stone/iron/coal, a farming region yields wool/cotton/leather) a real mechanical reason to exist, while urban scavenging keeps the original "upcycling" framing alive within the existing town. Each material — raw or salvaged — is an abstract `MaterialToken`, exactly like `EntityToken` — no hardcoded material colors in game logic.

**Cookbooks are how content is discovered, not unlocked by menu.** A recipe is not available from the start — it is *found* (a cookbook page in a workshop's back room, a salvage crate, a library shelf) or *earned* (taught by an NPC once trust crosses a threshold, rewarded by a quest). This makes recipes a content-discovery mechanic in the same family as the existing dialogue-tree and gossip systems, not a static crafting menu unlocked all at once. A player's known-recipes list is new per-save state, additive to `GameState`.

**Crafting stations live inside buildings — this is the seam to Pillar 2.** A workbench in the wood workshop, a forge in the metal workshop, a simple "maker bench" the player can eventually build at home. Not every recipe is craftable everywhere; higher-tier recipes need a station with the right tool, which is itself a reason to go enter a specific building — crafting and the buildings-as-plugins pillar are meant to pull the player through the world together, not sit as two separate menus.

**Depth example — the flagship "build a computer" chain**, taken directly from the user's own example, worked out concretely to show the system's real ambition rather than leave it as a slogan: scrap metal + wire → basic hand tools (a recipe found early, at the metal workshop); reclaimed wood + basic tools → a workbench/furniture piece (feeds Pillar 2's home-furnishing use case); glass + wire + electronic components → a simple radio (a nod to the existing "District Dispatch" broadcast flavor already in the game); radio-tier components + reclaimed plastic + a circuit board (itself crafted from etched copper + resin, a recipe gated behind a *found* cookbook, not given for free) → a working computer, which unlocks a genuinely new in-world affordance (a simple in-fiction terminal/BBS interaction, or a bridge into the existing crisis-news pipeline) rather than being a trophy item with no gameplay effect. The **bike** the user named explicitly follows the same shape at a shallower tier: scrap metal + rubber + reclaimed parts → an upcycled bike, either rideable (a lightweight, explicitly-deferred stretch goal, consistent with EPIC-31's own "rideable bike is a stretch item" note for M34) or sellable for cash through the existing economy hooks.

**Progression — skill, not just inventory, and a real values statement, not just a mechanic.** Crafting disciplines (Metalwork, Woodwork, Textiles/Leatherwork, Electronics, Horticulture/Foraging, Culinary) each track lightweight mastery, gating which recipes are craftable and improving output quality/sell price over time. This is one concrete answer to the user's "many ways to play": a player can lean hard into becoming the district's best metalworker without ever touching the Commons-resilience track, and still be making real, visible progress. It is also, deliberately, the game's central theme made mechanical rather than just narrated: per a direct follow-up from the user, the point of letting every player grow their own mix of learned skills is to make it concretely true — not just said in dialogue — that **a good community needs many different kinds of people**. No single discipline should be strictly optimal; the blacksmith, the weaver, the forager, and the person who mostly trades and organizes are all meant to be genuinely necessary to each other, the same way the existing Crisis Choice Framework already makes solidarity mechanically rewarding rather than just morally correct (CLAUDE.md). Concretely, this means recipes and crafting stations should be designed so that no one player can realistically master every discipline solo in a normal playthrough — real trading and mutual reliance between players (or, single-player, between the player and NPCs who hold their own disciplines) has to matter.

**A scope caution, raised by the user directly and worth stating plainly rather than waved away:** a skill system this open ("everyone can really begin to grow his own character") is a large, easily-unbounded design space for a project of this size. This vision's answer is to keep the *number of disciplines* small and fixed (the six named above, not an open-ended list) and let *depth within* each discipline be where the "growing your own character" feeling actually lives — mirroring how this project has repeatedly chosen a small, real, bounded slice over an unbounded promise (see every prior epic's Non-Goals). If mastery-tree depth turns out to want more room than that, it grows in a later milestone, not by widening scope now.

**Selling upcycled goods plugs into the existing economy, not a new one.** A crafted/upcycled item has a base sell value, adjusted by the crafting discipline's mastery level — sold through the same "Work"-style player-initiated action pattern M24 already established (`applyDailyTick()`/cash-earning actions), not a new parallel currency or market system.

## Pillar 2 — Buildings as Plugins: A Fine-Grained, Enterable World

Today, 14 building footprints exist on the map; only 3 have any interior at all, and those are a handful of colored rectangles drawn over the same shared tilemap with no real isolation (confirmed by EPIC-31's own audit). The user's ask is bigger than "fill in the other 11": buildings should become real, independently-developable pieces of the game, the same way minigames and skins already are.

**Every enterable building is exterior-plus-interior, loaded like a plugin.** On the worldmap, a building is a footprint with a roof (a real visual detail the current flat-color rectangles don't have — see Pillar 5) and a door. Entering it loads a dedicated interior scene/level — its own room layout, its own NPCs, its own goods and crafting stations — using the same dynamic-module-loading precedent `MinigameLoader`/`SkinRendererLoader` already proved works well in this codebase (`packages/building-*` as the natural home for larger or reusable building interiors, mirroring `packages/skin-*`/`packages/minigame-*`). Smaller, one-off building interiors can stay data-only definitions in `apps/web/src/world/` (extending `InteriorProps.ts`'s existing pattern), exactly as today — not every building needs to be a full package; the plugin option exists for the ones substantial enough to earn it (workshops with real crafting-station logic, multi-NPC retail spaces).

**A concrete building catalog**, again taken directly from the user's own list and extended to a realistic, buildable set: **Metalwork Workshop** (forge, scrap sorting — Pillar 1's metal-tier recipes and source materials), **Woodworking Workshop** (workbench, lumber stock — wood-tier recipes), **Baumarkt / Hardware Store** (buys/sells raw materials and basic tools — the retail anchor for Pillar 1), **Supermarket** (food, small daily-use goods, a second retail anchor distinct from the existing Corner Grocer's narrower flavor), **Library** (a genuine source of found cookbooks, tying back into the existing "civic" building family), plus the pre-existing building set (apartments, Town Hall, the Solar Quarter, the Tool Library) folded into the same generalized framework rather than left as a separate special case.

**This directly resolves — and broadens — EPIC-31's M33.** M33 already asked "extend the 3 existing interiors to all 14 footprints" and explicitly flagged interior-isolation as an open technical question to resolve before writing content. This pillar answers that question at the architecture level (real per-building loaded scenes, not just more colored rectangles on the shared tilemap) rather than the narrower scope M33 had planned, so M33's task doc is being superseded by this pillar's first milestone rather than implemented as originally scoped (see "Relationship to the Existing Roadmap" below).

**This also absorbs EPIC-32's Home & Housing plan.** A rented flat is, in this generalized model, simply one *type* of building interior the player has a lease on — and furniture is simply an application of Pillar 1's crafting/upcycling system (build or buy furniture rather than pick it from a fixed cosmetic catalog), which is a strictly richer version of what EPIC-32 planned. EPIC-32's genuinely good design decisions (map housing tradeoffs onto the existing stat quartet, no new "health" stat, recurring rent via the existing daily-tick hook) all carry forward unchanged; only the furniture mechanism gets deeper, and both land as one milestone inside this pillar's epic instead of a separate one.

## Pillar 3 — Open World: Regions Beyond the District

The entire game currently takes place on one hand-authored map. This pillar grows that into an actual **world** — not a procedurally generated open world (that would break the project's deterministic, headless-simulation foundation), but a WoW-style **region graph**: a set of distinct, hand-authored areas connected by travel points, each unlocked through play rather than all present from day one.

**Regions are additive, not a rewrite.** The current town becomes the starting region ("Common Ground"). New regions are added the same way M32 added biome variety to the existing map — deterministic, hand-placed content, never noise-generated terrain. A first realistic slate, chosen to each feed a different pillar rather than being cosmetic-only: an **industrial/scrapyard region** (rich in metal materials — feeds Pillar 1's metalwork chain and gives the Metalwork Workshop a narrative reason to exist there), a **rural/farming region** (plant-fiber and food materials, a second Culinary/Horticulture source), and a **forest/wilderness region** (wood and foraged materials, extending M32's park-pocket concept into a full biome). Each region gets its own tile-biome palette (extending `MapData.ts`'s tile system, not replacing it), its own building set (Pillar 2), and its own small NPC population.

**Travel is a real, literalized version of content that already exists in flavor.** The North Transit Hub's rail platform and cargo dock already exist as narrative dressing with no function (confirmed by the World Zones list) — this pillar gives them an actual job: fixed travel nodes connecting regions, unlocked by quest/trust/resilience milestones rather than currency, keeping progression tied to the game's existing solidarity-focused values rather than becoming a paywall.

**Regions can carry their own economy/crisis flavor**, reusing rather than duplicating the existing `CrisisEngine.ts`/`applyDailyTick()` machinery — e.g. an industrial region's crisis pool leaning toward workplace-safety/pollution scenarios, a rural region's toward climate/harvest scenarios — extending the existing scenario-pool pattern with a region tag, not building a second crisis system.

## Pillar 4 — Character Origin, Family & Identity

Today, "character creation" is picking one of 3 fixed archetype cards. The user wants the game to *open* differently: as being born.

**A short origin sequence, not a lifelong simulation.** The game begins with a small, deterministic family-background generator — a fixed, hand-authored library of family templates (economic circumstance, neighborhood tie-in, a starting relationship or two), selected the same non-random, seed-data way `crisis_scenarios.json` and `OUTDOOR_DRESSING_PROPS` are already "varied but not randomized." This is explicitly **not** a full birth-to-adulthood life simulation — the player still starts the game as a young adult ready to act in the world; the origin sequence exists to set narrative and mechanical *context* (which family, which starting circumstances, which starting relationships already exist in-world), not to be played through moment by moment.

**Real customization: name and identity, genuinely open.** A free-text name field, replacing the fixed "Pip/Morgan/Arthur" naming; a gender-identity selector that goes beyond a male/female binary (offering common non-binary options plus a free-text self-describe field, so "can also be diverse" is a real, respected option, not a cosmetic reskin of the same three archetypes); and an appearance choice (skin tone, hair, etc.) resolved entirely through the existing token/skin-manifest architecture, so no hardcoded appearance value ever touches game logic — appearance is cosmetic data, resolved to art only at render time, exactly like every other visual token in this codebase.

**Family background becomes the new source of starting stats, extending rather than deleting the existing archetypes.** The current Pip/Morgan/Arthur quartet doesn't disappear — it becomes 3 (of an eventually larger set of) family-background templates that determine starting cash/energy/trust/stress, now *named and explained* by the family story rather than picked as an abstract card. Family members can appear as real NPCs in the player's home region (a direct, concrete link to Pillar 2's housing and Pillar 3's regions — "your family's home" is a real building with real people in it, not narrative-only).

## Pillar 5 — Hi-Fidelity Art Direction (a Rayman-Inspired Pivot)

Every pixel in this game today is a canvas-drawn primitive — rectangles, gradients, one noise pattern — across all 8 existing skins, confirmed end-to-end by M30's own audit. The user wants to move toward real visual richness: layered, painterly, hand-crafted-feeling art, in the spirit of the newer *Rayman* games' polish — **not** a genre change. This stays a top-down game; the Rayman reference is about visual fidelity (painterly color, confident linework, dynamic lighting, a sense of depth through parallax and layering), not about becoming a 2D side-scrolling platformer. This explicitly narrows — not contradicts — EPIC-31's existing "no engine/perspective change" non-goal: the perspective and engine stay; the fidelity target changes.

**The existing multi-skin plugin architecture is exactly the right on-ramp, not a detour.** Because `SkinRenderer` is already a pluggable, dynamically-loaded contract (M30), the hi-fi pivot doesn't need to touch or destabilize the other 8 skins at all — it becomes one new flagship skin package first, proving the pipeline in isolation, promoted to default only once it's genuinely ready. This is the same "prove it as a plugin before it's load-bearing" discipline this project already used for every one of its last 4 major systems.

**The open, unresolved question, stated plainly rather than hand-waved:** where the actual art comes from. Three real options exist and are not equally cheap: (a) push the existing procedural-canvas technique further (better gradients, layered shading, hand-tuned lighting curves — zero new tooling, but a real ceiling on how "Rayman-like" pure code-drawn shapes can ever look); (b) build or commission real illustrated sprite/background assets and a matching atlas/animation pipeline (the only path to genuine Rayman-level fidelity, but a real, non-trivial production-and-tooling investment this vision does not pretend to have already solved); (c) a hybrid — hand-illustrated backgrounds/environment layers with procedural character rendering, or vice versa. This vision recommends starting with a small (b)-or-(c) proof — one flagship interior or one region rendered with real illustrated assets — specifically to answer this question with evidence before committing the whole game to one path.

## Pillar 6 — The Hub-and-Plugin Universe & Proximity Multiplayer

Added per a direct follow-up from the user, and it reframes how all five pillars above actually get *built*, not just what they contain: think of the base game as a small, stable **hub** — the core loop, the save/state system, the skin/token architecture — and think of every substantial piece of new content (a crafting discipline, a building, a region, eventually a whole new "universe" of content) as a plugin that *docks onto* that hub, the same way a browser tab docks onto a browser rather than being compiled into it.

**This is not a new idea for this codebase — it is the existing pattern, generalized on purpose.** Minigames (M14/M29) and skin renderers (M30) already work exactly this way: a typed contract, a manifest, a dynamically-`import()`ed standalone bundle built by its own `packages/*` workspace package. [Pillar 2](#pillar-2--buildings-as-plugins-a-fine-grained-enterable-world) already proposed the same shape for buildings. This pillar's contribution is to say explicitly: that should be the *default* way this whole vision gets implemented — crafting disciplines, region packs, and building sets are all, architecturally, "just another plugin docking onto the hub" — rather than leaving the plugin pattern as something only Pillar 2 uses.

**Standalone-container hosting is a real, already-partially-true next step, not a leap.** The Docker Compose stack (`docker-compose.yml`/`docker-compose.dev.yml`) already runs `web`/`api`/`db` as separate services; plugin bundles are already served as static files the web container mounts. The natural next increment — explicitly a later, infrastructure-focused milestone, not assumed solved here — is a plugin able to run as its *own* container/service in the same stack (a region's content server, a workshop's crafting-logic service), reachable the same way the API is today, rather than only ever being a static frontend bundle. Hosting a plugin on a remote server, or eventually a peer's own device, is the same idea taken one step further — again, named as a direction, not committed to in this vision's first milestones.

**Proximity multiplayer — visiting another real player's shop or home — is the concrete, buildable core of this pillar, and it already has real infrastructure to stand on.** This game already has a working, tested mesh-networking layer: `MeshTransportPlugin` (`packages/shared-types/src/mesh.ts`), a pluggable-transport contract with peer discovery (`PeerDescriptor`), signed multi-hop packet relay (`MeshPacket`, TTL-based), and channel routing (`MESH_CHANNELS`), built across M17–M19 specifically so BitChat/LoRa/BLE/local-WiFi transports can all plug into the same core without the game caring which one is active. It also already has a *permissioned visiting* precedent: `FriendDistrictViewer.ts`/`SocialHubModal.ts` (M15) already let a player view a friend's district read-only, over the normal API. Pillar 6's proximity feature is the natural synthesis of both: when a nearby peer is discovered over an active mesh transport, and that peer has opted their building/home in as visitable, the visitor can enter it — read-only at first (mirroring `FriendDistrictViewer`'s existing, already-proven read-only precedent), never a surprise, always opt-in per building, never a default.

**A player choosing to "run" a plugin for only part of a session is a real, supported idea, not a stretch.** Because plugins are already independently loaded modules with their own lifecycle (`init()`/`destroy()` on `MeshTransportPlugin`; dynamic `import()` on `MinigameLoader`/`SkinRendererLoader`), a region, crafting-discipline, or building plugin being loaded only while the player is actually using it — a few hours a day, as the user put it — is a natural consequence of the architecture already in place, not a new capability that has to be invented.

**A direct answer to the user's own "is this too broad" question, since they asked it explicitly:** yes, taken as a whole and pursued all at once, this is too broad — which is exactly why it is being scoped as the *last* pillar, in the *smallest* epic (2 milestones, not 3), and split so its first milestone only generalizes the existing single-player plugin pattern (Pillar 6's architectural half), while genuine live proximity multiplayer between two real players — the hardest, highest-uncertainty part — is its own second milestone, explicitly allowed to be scoped down to a small proof (one visitable building type, one transport) rather than a full feature, and explicitly allowed to slip behind every other pillar in build order without blocking them. Every other pillar (1–5) is designed to work completely, end to end, in pure single-player, exactly as the whole game does today — Pillar 6 is additive polish on top, never a dependency the others wait on.

## Cross-Cutting Systems & Principles

- **Cookbooks are the connective tissue across Pillars 1, 2, and 3.** A recipe found in one region's Baumarkt might only be craftable with materials sourced from a different region — this is the concrete mechanism that makes "open world" and "deep crafting" reinforce each other instead of sitting side by side as two unrelated features.
- **"Many ways to play" is a real design commitment, not a slogan.** Progression branches beyond the existing Commons-resilience track: a crafting-mastery path (Pillar 1), a trade/retail path (Pillar 2's shops), an exploration/region-unlocking path (Pillar 3), alongside the existing social/solidarity track — a player can meaningfully specialize.
- **Determinism is non-negotiable and applies to every pillar, including "random" family generation.** Per CLAUDE.md's headless-simulation philosophy, nothing in this vision introduces true per-playthrough randomness — material spawn points, family templates, region content, and cookbook placement are all hand-authored, fixed, seed-style data, "varied" the same way `OUTDOOR_DRESSING_PROPS` and `crisis_scenarios.json` are varied: by authoring more of it, not by rolling dice.
- **The token/skin architecture is non-negotiable and applies to every pillar too.** Materials, recipes, buildings, regions, and character appearance all resolve through abstract tokens and `skin.manifest.json`, never hardcoded colors/asset names in game logic — this is what keeps the eventual Pillar 5 art pivot possible without a game-logic rewrite.
- **The plugin/package precedent is the default implementation shape for the whole vision, not a one-off for buildings.** Per Pillar 6, crafting disciplines, region packs, and building sets are all, by default, `packages/*` plugins docking onto the hub, exactly like `packages/minigame-*` and `packages/skin-*` already do — not just the buildings Pillar 2 originally named.
- **Single-player always comes first and always fully works.** Every pillar's core content is built and playable with zero other players present, exactly as the whole game is today; multiplayer proximity visiting (Pillar 6) is additive and never a dependency the other five pillars wait on.

## Relationship to the Existing Roadmap — What Changes

- **EPIC-31's M31 and M32 stand as implemented and unaffected.** M32's tile/biome work is direct infrastructure for Pillar 3's regions.
- **EPIC-31's M33 (Real Building Interiors) is superseded by the new EPIC-34's first milestone**, which resolves the same open interior-isolation question M33 flagged, but at the generalized "buildings as plugins" scope this vision calls for rather than the narrower "add props to the other 11 footprints" scope M33 was originally written at. M33's task doc is marked superseded, not deleted — its investigation-first framing was correct and is carried forward.
- **EPIC-31's M34 (Street Life) and M35 (Quest/Progression) are kept exactly as planned**, unaffected by this vision; M35 should eventually add cookbook-discovery as a quest-reward type (a cross-reference for whenever it's built, not a merge).
- **EPIC-32 (Home & Housing, M36/M37) is folded into the new EPIC-34's third milestone.** Its design decisions carry forward unchanged (no new health stat, recurring rent via the existing tick hook); only the furniture mechanism is upgraded from a fixed cosmetic catalog to an application of Pillar 1's crafting system. The `M36`/`M37` numbers are retired, not reused, to avoid any future confusion with the superseded draft.
- **New work continues at M38**, across 6 new epics (`EPIC-33`–`EPIC-38`): 3 milestones each for `EPIC-33`–`EPIC-37` (`M38`–`M52`), plus 2 milestones for the smaller, deliberately-last `EPIC-38` (`M53`–`M54`) — see each epic doc under `docs/stories/` and each milestone's task doc under `docs/tasks/` for the audited, actionable breakdown of everything above.
- **`EPIC-38` (Hub-and-Plugin Universe & Proximity Multiplayer) builds directly on the existing, already-shipped M17–M19 mesh-networking work and M15's friend-district-visiting feature**, rather than proposing new infrastructure from scratch — see its own epic doc for the exact grounding.

## Non-Goals (vision-wide)

- **No true procedural/random generation anywhere** — not in region terrain, not in family generation, not in material placement. Everything stays hand-authored and deterministic, consistent with every prior milestone in this project.
- **No engine rewrite, no move to 3D, no becoming a side-scrolling platformer.** Pillar 5 is about fidelity, not genre.
- **No real-money marketplace, no NFT-style item ownership.** Upcycled goods sell for in-game cash through the existing economy only.
- **No promise that "everything" is craftable in v1.** Breadth grows milestone by milestone, the same disciplined way every prior epic in this project shipped a bounded real slice rather than an unbounded one.
- **The family/origin system does not retroactively rebalance the existing Pip/Morgan/Arthur archetypes** — it's an additive framing and expansion layer, not a rebalance pass.
- **Pillar 5's art-sourcing question is explicitly left open here**, flagged for a real decision at its own milestone (M50) rather than assumed away.
- **Pillar 6's live proximity-multiplayer half is explicitly allowed to ship as a small proof, not a full feature**, and never blocks any of the other five pillars — see the direct "is this too broad" answer in Pillar 6's own section above.
- **The number of crafting disciplines (Pillar 1) is fixed at six for v1**, not open-ended, for the same reason.
