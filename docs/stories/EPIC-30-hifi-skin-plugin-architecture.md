# EPIC-30 — Hi-Fi Procedural Skin Plugin Architecture

## Origin

The user asked to "replan the whole style of the game": keep the existing retro/Game-Boy-style skin (their Zelda: Link's Awakening reference) as one option, but add a genuinely new, "very well designed," 2026-quality hi-fi visual style as another. Three concrete art directions were pitched back — Diorama Glow, Flat Vector Minimal, Neon Night-City — and the user's reply was "all of this sounds very nice! can we have them all planned in tickets and let them load into the game via plugin system?" — i.e. build all three, and load them the same dynamically-imported-bundle way [EPIC-29](EPIC-29-minigame-plugin-architecture.md) made minigame code load, not compiled into the main bundle.

Before writing this ticket, the current skin system was audited end-to-end (`ThemeManager.ts`, `SkinInterface.ts`, `ThemePluginManager.ts`, `WorldScene.ts`'s texture-generation functions, `apps/api/internal/theme/handler.go`) to find out what a "skin" actually controls today, rather than designing against what the code's own comments claimed.

## Design Intent — the real gap this closes

Every one of the 5 existing skins (`solarpunk`, `retro_gb`, `aurora`, `labor_woodcut`, `sunset_commons`) is a JSON-only manifest: 9 world-tile hex colors, a UI-chrome token set (fonts/radius/shadow/gradient), and 2 audio-profile label strings. None ship real texture files — every `SkinManifest.assetMap` entry points at a `.webp` path that doesn't exist on disk anywhere in the repo, and `ThemeManager.switchSkin()` only swaps a Phaser texture "if the atlas files are actually loaded" (a `HEAD` check that always fails today, by design — see its own comment). The actual pixels every skin produces come from exactly 3 hardcoded functions in `WorldScene.ts` — `createTilesetTexture()`, `createPlayerTexture()`, `createNPCTextures()` — and only the first even reads the palette; hero and NPC sprite colors are hardcoded hex literals, byte-for-byte identical across every skin. So today, "switching skins" only ever recolors floor/wall/road/plaza/door tiles — it never changes what the hero, NPCs, or buildings look like, and there is zero lighting, gradient, or particle work anywhere in the renderer (grepped the whole frontend: zero `ParticleEmitter`/`addLight`/`Pipeline`/`.glsl` usage; all "juice" — streetlamps, day/night tint, ambient warm light — is plain `Graphics`/`Rectangle`/`Arc`/`Ellipse` primitives or a separate multiply-blended HTML canvas layer, `AmbientLightLayer`).

A genuinely new "hi-fi" skin needs to change all of that — tile shading, hero/NPC silhouettes, ambient glow — which means it needs to ship real drawing *code*, not just palette data. And per the user's plugin-system ask, that code must load the way EPIC-29 made minigame code load: a standalone bundle, dynamically `import()`ed at runtime, decoupled from the main app bundle — not a 4th/5th/6th hardcoded function bolted onto `WorldScene.ts` next to the existing 3.

This is what M30 builds: a new `SkinRenderer` plugin contract (mirrors `MinigameModule`/`MinigameLoader` exactly) that lets a skin package export its own `createTilesetTexture`/`createPlayerTexture`/`createNPCTextures`, built via the same Vite-lib-mode pipeline as the 5 minigame packages, and loaded via a new `SkinRendererLoader.loadRemoteSkinRenderer()`. The 5 existing palette-only skins keep working completely unchanged — no `rendererUrl` in their manifest means `WorldScene` falls back to today's 3 hardcoded functions, exactly as now. The 3 new hi-fi skins each ship a real renderer package with genuinely different draw code, not just different hex values:

- **Diorama Glow** — warm single-key-light gradients baked into every tile fill, long soft blurred shadows, rounded toy-diorama hero/NPC silhouettes. (This is the Zelda: Link's Awakening *2019 remake*'s look — the original Game Boy look the user said was "ok as-is" is already covered by the existing `retro_gb` skin, untouched here.)
- **Flat Vector Minimal** — confident 2–3 tone flat color blocking per tile, a precomputed subtle grain/noise overlay, bold geometric capsule-shaped hero/NPCs. No dithering or per-pixel speckle.
- **Neon Night-City** — near-black grounds, emissive glow edges on walls/doors/hero via layered alpha strokes (the same technique the existing streetlamp `ADD`-blend glow already uses), high-contrast angular silhouettes.

All 3 stay within the Phaser `Graphics`/Canvas2D texture APIs already used everywhere in `WorldScene.ts` today — no WebGL shaders, no Light2D pipeline. That's a deliberate honesty check on scope: this will read as a well-executed stylized 2D indie look, not a hand-painted or ray-traced one, and it's achievable without introducing a new rendering subsystem or any external art pipeline.

## Non-Goals

- **Hand-drawn or externally-generated art assets.** No image-generation tool is available in this workflow; all 3 hi-fi skins are procedural (code-drawn), like every existing skin. `SkinManifest.assetMap`'s real-texture-swap path stays available (unused today, unused by this milestone) for a future skin that does ship real files.
- **Sandboxing renderer code for future community-submitted hi-fi skins.** The 3 new skins are first-party and trusted, same as the 5 existing built-ins — no sandboxing needed for them. But the `rendererUrl` mechanism this milestone adds means a *future* community theme could ship arbitrary code with direct Phaser scene access — a materially bigger trust problem than today's data-only community-theme manifests (`ThemePluginManager.registerRemoteThemeManifest()` only ever fetches JSON, never executes code). That risk is flagged here for whoever picks up community-submitted renderers later; it is not solved in this milestone, and not silently ignored either.
- **Changing hero/NPC hitboxes, animation timing, world layout, or any simulation logic.** Purely a rendering-layer change — `PlayerEntity`, `NPCEntity`, `CollisionSystem`, `EconomyMath`, etc. are untouched. The existing animation definitions (`walk_down`/`walk_up`/`walk_left`/`walk_right`, keyed to 8 fixed frame indices on the `'player'` texture, and 6 fixed frames on `'npcs'`) fix the frame *layout* every renderer must produce — only the pixels inside each frame change.
- **Retiring or changing the 5 existing palette-only skins.** They keep working through the exact same code path as today; zero behavior change for them is a hard requirement, not a side effect.
- **The dead "Cozy Vector" placeholder card in `SettingsModal.ts`.** Repurposed as part of wiring the 3 new skins into the picker (M30 §7) rather than left as a separate cleanup task — it was a stretch goal from M5 that was never built.
