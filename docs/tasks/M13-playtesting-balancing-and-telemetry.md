## 1. `BalanceSimulator.ts` — deterministic 90-day solvency sweep

- [x] New `apps/web/src/core/simulation/BalanceSimulator.ts` — `runSolvencySweep(archetype, days, seed, commons?, multipliers?)`, calling `applyDailyTick()` once per simulated day, threading cash/energy/stress forward exactly like `advanceDay()` does, headless (no store, no save). `ARCHETYPE_SEEDS` was exported from `actions.ts` rather than re-typed here, so the sweep starts from the exact same Day-1 numbers the real game seeds — avoiding the "second hand-copied table drifts out of sync" failure mode M22 hit with its 3 built-in-skin-list copies.
- [x] Baseline scenario: `DEFAULT_MULTIPLIERS`, per archetype, from `ARCHETYPE_SEEDS`, with a fixed `commons` snapshot per sweep (`UNBUILT_COMMONS`/`FULLY_BUILT_COMMONS` exported constants) — see the note below on why the sweep doesn't grow commons progress over time itself.
- [x] "Permanent Inflation" scenario (`PERMANENT_INFLATION_MULTIPLIERS`: `food: 1.5`). **Deviation from the plan, discovered during implementation:** the spec's `energy: 1.75` is set on the exported constant for fidelity to the doc, but it is a documented no-op — `applyDailyTick()` never reads `multipliers.energy` anywhere (grepped every consumer: only `food`, `wage`, and `transit` feed the daily cash/energy math; `energy`/`heat`/`migrant` are read elsewhere for HUD display, weather, and crisis frequency respectively, never for the tick itself). Faking an effect here would have been worse than documenting the gap.
- [x] "Algorithm Pay Slash" scenario (`ALGORITHM_PAY_SLASH_MULTIPLIERS`: `wage: 0.7`) — Pip only; Morgan/Arthur don't read `multipliers.wage` at all, so they're the control by construction, not by test setup.
- [x] `BalanceSimulator.test.ts` — Tests 13.1/13.2/13.3, 8 tests. **Deviation from the plan, discovered during implementation:** the spec's illustrative Day 30/60/90 dollar targets (e.g. Pip "$120 cash by Day 30") don't hold against the real formulas at all — computed by hand and confirmed by running the tests: Pip's baseline unbuilt trajectory is `cash = 25 + 2×day` (Day 30 = $85, not $120), because the sweep holds `commons` fixed rather than growing it mid-run (a player who never contributes to the commons is the worst case, which is what a *fixed*-input sweep necessarily models — see `runSolvencySweep`'s doc comment). The real, useful finding baked into the tests instead: energy/stress saturate at their clamps within ~4–14 days for every archetype under baseline, and a fully-built commons set inverts Arthur's stress trajectory from climbing to falling. These are the new regression baseline, per M8's "formally re-scoped, reconcile spec claims against real code" precedent.
  - **Further deviation:** the spec's "Permanent Inflation Run: unorganized players go bankrupt by Day 18" claim also doesn't hold — at `food: 1.5` alone, no archetype's `cashDelta` goes negative at baseline wage/transit (foodCost only rises to $4–5/day, well under any archetype's earnings). What *does* hold exactly as claimed is the protective mechanism: a built Kitchen makes `cashDelta` completely invariant to the food multiplier (`foodCost` is hardcoded to `0` once `kitchenProgress >= 100`, multiplier or not) — asserted directly in Test 13.2's second case.

## 2. Telemetry — extended the existing M18 signed event log, not a new pipeline

- [x] `packages/shared-types/src/offline.ts`'s `SyncActionType` union — added `CRISIS_RESOLVED`, `COMMONS_MILESTONE`, `LAND_TRUST_RATIFIED`. No changes needed to `CRDTSyncEngine.ts`: `resolveOrSet()` is already generic over `actionType`, so all three telemetry events resolve as an OR-Set (add-only, never revoked) for free, exactly like `IRL_DEED_LOGGED`.
- [x] **Deviation from the plan, discovered during implementation:** the plan said to wire `CRISIS_RESOLVED` into `apps/web/src/core/state/actions.ts`'s `resolveCrisis()` — but that function turned out to be **dead code**, never called by any real UI path (only its own tests and the identically-named-but-different `CrisisEngine.ts`'s `resolveCrisis()` exist; `CrisisWireModal.ts`, the actual crisis modal, imports and calls `CrisisEngine.ts`'s version). Wiring the dead one would have produced a task-doc checkbox that lied about coverage. Wired `recordAction('CRISIS_RESOLVED', { crisisId, archetype, choice, dayNumber, resilienceBefore, trustDelta })` into the real `CrisisEngine.ts::resolveCrisis()` instead, snapshotting `resilienceBefore` (`state.commons.resilienceScore`) before any consequence lands, and computing `trustDelta` as the *total* trust change including the extra −15 scapegoat penalty applied later in the same function (`c.trustDelta + (isScapegoat ? -15 : 0)`), not just the scenario's raw `consequences.trustDelta`.
- [x] `updateCommonsProgress()` in `actions.ts` — detects the exact tick a node first crosses 100% and fires `COMMONS_MILESTONE`. **Deviation:** field names changed from the spec's `daysToComplete`/`totalDonationsCash`/`energySpent` to `completedOnDay`/`contributionAmount` — per-node cumulative totals and a "day this node's build started" timestamp aren't tracked anywhere in `GameState` today, and adding new persisted state just to match the spec's exact field names would have been scope creep for a testing/telemetry milestone. `completedOnDay` mirrors the naming already used by `QuestState.completedOnDay` elsewhere in this codebase.
- [x] The `safeHavenUnlocked` flip inside `updateCommonsProgress()` — fires `LAND_TRUST_RATIFIED` with `{ completedOnDay, globalResilience, playerTrustScore }`. **Deviation:** `arthurTrustScore` → `playerTrustScore` (generalized — any archetype can be the one who ratifies the Land Trust, not only Arthur; the spec's own framing was loose here). `totalDays` → `completedOnDay` for the same reason as above.
- [x] `TelemetryEvents.test.ts` (new file, `apps/web/src/core/state/`) — Test 13.4: all three call sites, mocking `offlineRuntime`'s `recordAction` directly (isolated from the real Ed25519/IndexedDB signing path, which `SignedEventLog.test.ts` already covers) and asserting no PII-shaped keys ever appear in a payload. 3 tests, all passing.

## 3. New backend surface — economic snapshot log (the one real new piece)

- [x] `apps/api/internal/db/migrations/012_create_economic_snapshot_log.{up,down}.sql` — mirrors `crisis_log`'s exact shape (`id UUID`, `user_id UUID REFERENCES users(id)`, `day INT`, `archetype TEXT`, `cash INT`, `energy INT`, `created_at`, indexed on `(user_id, day)`). No free text, no PII. Verified applying cleanly against a real Postgres 17 container via `testutil.NewPostgres`.
- [x] `apps/api/internal/save/economic_snapshot.go` — `EconomicSnapshotHandler` with `HandleRecordSnapshot` (`POST /api/v1/district/economic-snapshot`, auth required, validates `archetype ∈ {pip, morgan, arthur}` and non-negative cash/energy) and `HandleAttritionRate` (`GET /api/v1/district/attrition`, public, cached, `attritionRate` = % of distinct users with any `(cash=0 OR energy=0) AND day<10` row, out of all users with any row) — same shape/error-handling/nil-pool-safety conventions as `solidarity_pool.go`.
- [x] Frontend: `district.ts`'s new `recordEconomicSnapshot()` + `advanceDay()` in `actions.ts` — fire-and-forget POST of the day's post-tick `{day, archetype, cash, energy}`, guarded on `classRole` being set (skips the pre-character-select state rather than recording garbage).
- [x] `economic_snapshot_test.go` — Test 13.5 plus 4 supporting unit/validation tests. All pass, including 2 Docker-integration tests proving the real write path moves the real read aggregate (mirroring `solidarity_pool_test.go`'s `EndToEnd_ChangesAggregate` pattern) and a day-≥10 case proving the window boundary is exact.
- [x] Wired into `apps/api/cmd/server/main.go`: both routes registered alongside the existing `/district/*` routes.

## 4. Per-scenario solidarity breakdown

- [x] `apps/api/internal/save/solidarity_pool.go` — new `HandleResilienceByScenario` (`GET /api/v1/district/resilience/by-scenario`, sibling to `HandleDistrictResilience` rather than a modification of it, so the existing global-aggregate response shape stays untouched) — `GROUP BY crisis_id` over the same `crisis_log` table, returning per-scenario `solidarityCount`/`scapegoatCount`/`solidarityRatio`/`skewed` (the spec's >85%/<15% rule, computed as a boolean flag).
