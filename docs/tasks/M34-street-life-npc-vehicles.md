# M34 — Street Life: Moving NPCs, Pedestrians & Vehicles

Story: [`docs/stories/EPIC-31-world-hud-progression-overhaul.md`](../stories/EPIC-31-world-hud-progression-overhaul.md)

Planning: none new under `docs/planning/` — scoped ad hoc from a direct user request to move the game from a "Gameboy Zelda" feel toward a "GTA" direction (people on the street, bikes, cars), grounded by an Explore-agent audit confirming `NPCEntity` has zero movement code and no Vehicle/Car/Bike entity type exists anywhere in the codebase.

Status: **Implemented.** The last milestone from EPIC-31's original M31–M35 breakdown (M31/M32 shipped 2026-09-19; M33 was superseded by EPIC-34/M41; M35 follows next).

## Section 1 — Give NPCs real movement

`apps/web/src/world/entities/NPCEntity.ts` (was: positioned once, `update()` only measured distance to the player — no movement code at all):
- [x] Added waypoint-style wander confined to each NPC's home zone (a `wanderRadius` around the original spawn `position`, now treated as a "home" anchor). **Decision, recorded rather than left open**: wall/prop avoidance uses a lightweight injected `isWalkable(x, y)` tile-grid lookup (`WorldScene.isWalkableWorldPos()`, backed by the same `MapData.ts`/`isWalkableTile()` the tilemap's own collision layer uses), not `CollisionSystem.ts`'s `physics.add.collider` — confirmed by reading it that this only colliders a real Arcade *physics* sprite against the tilemap layer, and NPCs remain plain (non-physics) `Image` objects; converting all 6 to physics bodies just to reuse it would be a disproportionate lift for slow ambient wander, and the task doc's own wording explicitly allowed this lighter-weight alternative. `NPCEntity` stayed fully Phaser-free (its existing design, kept deliberately rather than switched to `PigeonEntity`'s Phaser-owning shape) specifically so wander-stays-in-radius and talkability-while-moving are unit-testable without a scene.
- [x] Talk-prompt/dialogue keeps working unchanged while mid-wander: `update(playerX, playerY)` now measures proximity from the NPC's live `x`/`y` (updated by the new `tick()`) instead of the static home `position` — the one real behavior change, proven by a new test that walks an NPC away from its spawn point and confirms the player still triggers `isActive` by standing at its *current* location, not its original one. `WorldScene.ts`'s per-frame loop now also syncs the owned `Image`/`InteractionPrompt` to `npc.x`/`npc.y` each frame (the drop-shadow already tracked the `Image`'s own position via `updateShadowsAndLight()`, so it rides along for free — that call was reordered to run *after* the new npc/pedestrian tick block so shadows read the current-frame position, not a stale one).
- [x] Confirmed via grep, before changing anything, that no test file referenced `NPCEntity` at all (`NPCEntity.test.ts` didn't exist) — zero regression risk from a "NPCs are stationary" assumption anywhere.

## Section 2 — Background pedestrians

New `apps/web/src/world/entities/PedestrianEntity.ts` (lightweight, not a full `NPCEntity` — no dialogue/gossip/quest state):
- [x] Non-interactive wander extras, Phaser-owning (mirrors `PigeonEntity`'s shape, not `NPCEntity`'s Phaser-free one — no dialogue-critical logic here worth isolating for a unit test, and no dedicated test file exists for `PigeonEntity`/`ScrapsEntity`/`PlayerEntity` either, the same established precedent). **Deliberately reuse the existing `'npcs'` spritesheet texture** (already generated per-active-skin by `DEFAULT_RENDERER`/every hi-fi package's `createNPCTextures()`) rather than building a second texture atlas or extending the `SkinRenderer` plugin contract for a 4th texture kind — this satisfies the doc's own "reuse the NPC texture-generation approach, not a new art pipeline" wording literally, means pedestrians automatically match whichever skin is active with zero new hardcoded color, and avoids an 8-package contract-extension lift (5 legacy + 3 hi-fi renderers) disproportionate to purely-cosmetic background dressing. Visually distinguished from the 6 talkable named NPCs with a runtime `setAlpha(0.85)` + a muted multiply `setTint()` — a per-instance Phaser render property, not a new palette/hex baked into a texture, the same category as the shadow ellipses' existing fixed `0x000000` used everywhere regardless of skin — so this stays consistent with `CLAUDE.md`'s Critical Architecture Rule (game logic still never hardcodes a skin-specific asset/color; the tint is generic "background" presentation polish, not asset selection).
- [x] 15 pedestrians total (3 per zone × 5 zones — North Transit Hub, Central Plaza, South Quarter courtyard, East Canal walkway, South Solar Quarter plaza), well above the 6 named NPCs per the doc's "greater numbers" ask, populating every outdoor zone rather than clustering all of them where the existing pigeons already are. **Frame-budget sanity check** (not a full profiling pass, per the doc's own scoping): each pedestrian is one plain `Image` + one `Ellipse` with no Arcade physics body and an O(1) per-frame `tick`/bounds-clamp/tile-lookup — the same cost class as the 4–6 `PigeonEntity` instances already running in this scene since M23 with no reported issue, just ~3x the count; `npm run build`'s bundle size is unaffected (no new dependencies, ~80 lines of plain TS) and the production build stayed clean. A full Lighthouse/profiler pass wasn't run (no headless browser available in this environment, the same limitation recorded for every prior visual milestone), so this is an engineering-judgment sanity check, not a measured guarantee — flagged explicitly rather than silently assumed safe.

## Architecture notes / non-goals

See [EPIC-31](../stories/EPIC-31-world-hud-progression-overhaul.md)'s epic-wide non-goals — no traffic simulation, no vehicle collision physics, no AI-driven traffic actually navigating the road network; none were built. Confirmed upheld: NPC/pedestrian wander is simple radius/bounds-clamped random-direction movement with a tile-walkability bounce-back, not pathfinding or steering behavior, and vehicles stay exactly the pre-existing static decoration. Game logic never references a sprite filename or hardcoded hex for pedestrians/vehicles — pedestrians route entirely through the existing skin-resolved `'npcs'` texture, and vehicle tokens (`PROP_PARKED_CAR`/`PROP_PARKED_BIKE`) were already `OutdoorPropToken`-driven before this milestone.
