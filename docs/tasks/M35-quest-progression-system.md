# M35 — Real Quest & Progression System

Story: [`docs/stories/EPIC-31-world-hud-progression-overhaul.md`](../stories/EPIC-31-world-hud-progression-overhaul.md)

Planning: none new under `docs/planning/` — scoped ad hoc from a direct user complaint ("there need to be real quests to solve in every level so there is a progress"), grounded by an Explore-agent audit confirming the existing `IrlQuestSystem` is a self-attested daily buff with zero location/NPC linkage, and that `GameState` has no level/chapter concept anywhere today.

Status: **Implemented.** The final milestone from EPIC-31's original M31–M35 breakdown — M31/M32/M34 are done, M33 was superseded by EPIC-34/M41; EPIC-31 is now fully resolved (implemented or superseded) end to end.

## Section 1 — Establish a "level" concept without inventing a parallel system

`apps/web/src/core/simulation/WorldQuests.ts` (new):
- [x] Reused the existing Commons build-node progress track as the game's "level" structure — no `level`/`chapter` field was added to `GameState`. No new state, purely a reframing.
- [x] **The zone ↔ build-node mapping, documented explicitly (not left implicit) and grounded in the real code, not narrative guesswork**: read `WorldScene.create()`'s construction-node marker coordinates against `WorldScene.updateZone()`'s own zone-boundary thresholds. `solar`'s marker (row 8) sits in `'North — Transit Hub'`; `legal`/`toolLibrary`/`landTrust`'s markers (rows 31/30/36) all sit in `'Central Plaza'`; `kitchen`'s marker (row 58) sits in `'South Quarter'`. Two zones needed an explicit, recorded decision since no marker sits inside them: `'South Solar Quarter'` → `solarGridProgress` anyway (shared with the North zone), since `CLAUDE.md`'s own World Zones description places the Solar Co-op's actual payoff (completed solar field, greenhouse) physically there — the Solar Co-op "level" narratively spans both zones. `'East Canal'` → the aggregate `resilienceScore`, since it has no construction node in or near it and no zone lore ties it to one — the honest choice over forcing an arbitrary unrelated node. The full `ZONE_BUILD_NODE` map and its reasoning live in `WorldQuests.ts`'s own doc comment, and are proven, not just asserted, by a real test (`WorldQuests.test.ts`'s "maps every one of `WorldScene.updateZone()`'s 5 real zone strings to a real commons field").

## Section 2 — New location-verified objective type, separate from `IrlQuestSystem`

New `apps/web/src/core/simulation/WorldQuests.ts` (`IrlQuestSystem.ts` untouched, exactly as scoped) + wiring in `apps/web/src/core/state/actions.ts`:
- [x] New `WorldQuestId`/`WorldQuestState` types live in `useGameStore.ts` (a brand-new top-level `worldQuests: { activeId, completedIds }` slice, safe against old saves with no migration code needed — the same established pattern every prior brand-new slice since M38 has used); the richer `WorldQuestDefinition`/`WorldQuestTarget`/`WorldQuestReward` types and the 3 concrete quest definitions live in the new pure `WorldQuests.ts` module, which deliberately has **zero `useGameStore` import** — see its own doc comment for why (avoiding a real circular import with `actions.ts`, which is the file that has to call the real `updateCommonsProgress()` for a quest's commons bonus). Naming avoids any collision with the existing `QuestId`/`QuestState` (`IrlQuestSystem.ts`'s own types), per the doc's own ask.
- [x] 3 concrete `WorldQuest`s ship, one per target kind the doc names (proving the mechanism end to end, matching this project's established "prove the mechanism first" scoping rather than building exhaustive content): `scout-the-transit-hub` (`reach-zone`, verified via `WorldScene.updateZone()`'s own real per-frame zone string — `checkZoneWorldQuestProgress()`), `deliver-higgins-letter` (`talk-to-npc`, verified on `DialogueOverlay`'s `onClose` — i.e. the player actually *finished* a conversation with the target NPC, not just opened the overlay — `checkTalkWorldQuestProgress()`), and `fund-the-kitchen` (`build-node-threshold`, verified by reading the real post-update `commons.kitchenProgress` value straight off the store inside `updateCommonsProgress()` itself, so it can never drift from what actually landed — `checkBuildNodeWorldQuestProgress()`, called on every single commons contribution regardless of source). None of these read a self-attested "Done" button anywhere.
- [x] Completion rewards apply the same way `IrlQuestSystem.completeQuest()` already does (a direct player-stat `setState`, cash/energy/trust/stress), plus — `fund-the-kitchen` specifically — a **real** `commonsBonusNode`/`commonsBonusAmount` reward applied through the exact same `updateCommonsProgress()` every ordinary build-node contribution goes through (not a second bespoke commons-mutation path), closing the Section 1 loop: completing this quest visibly advances `commons.kitchenProgress` by a further +5 on top of whatever contribution actually crossed the threshold. Proven by a real test asserting the exact post-completion `kitchenProgress` value (45 + 10 + the 5 bonus = 60), not just that *some* number changed.

## Section 3 — Quest log / objective tracker HUD element

`apps/web/src/ui/TopHUD.ts`:
- [x] New `#hud-objective` chip, in the same passive-readout spirit as the existing `#hud-zone`/`#hud-barometer` elements — reflects `state.worldQuests.activeId` directly off the store on every `render()` call (never a separately-tracked UI-only copy that could drift), distinct from `QuestModal`'s existing daily-buff list, visible without opening anything.
- [x] Degrades gracefully: `hidden = true` (not just emptied) whenever `worldQuests.activeId` is `null` — proven by the "no WorldQuest active" test case in `WorldQuests.test.ts` (`checkZoneWorldQuestProgress` with nothing active leaves `completedIds` empty, and by inspection `activeQuest` resolves `undefined` so `render()` takes the hide branch) plus the class's own established `hidden`-attribute convention every other conditional HUD element already uses (`pulseBadgeEl`/`barometerEl`/`walletChipEl`).

## Section 4 — Quest-giver wiring

`apps/web/src/world/NpcDialogues.ts` + `apps/web/src/ui/DialogueOverlay.ts` + `apps/web/src/world/WorldScene.ts`:
- [x] `DialogueNode` gained an `assignsQuest?: WorldQuestId` field, extending the exact same small, fixed mechanism M39's `teachesRecipe`/`minTrust` already built (no new dialogue-gate system) — `DialogueOverlay.renderNode()` fires `onAssignQuest?.(node.assignsQuest)` the moment such a node renders, independent of `teachesRecipe` (a node may carry both, as `higgins_memory` now does). Wired into 3 of the 6 named NPCs' own `*_intro` trees (the same tree M39's `teachesRecipe` nodes already live on, for the same "reliably reachable early" reason): Leo (`leo_legal` → `scout-the-transit-hub`), Higgins (`higgins_memory` → `deliver-higgins-letter`, alongside her existing `RECIPE_MENDED_JACKET` teach), and Mira (`mira_kitchen` → `fund-the-kitchen`) — plain flavor-text additions to each node's existing dialogue, not new trees. `WorldScene.openTalk()` supplies the real callback (`assignWorldQuest(questId as WorldQuestId)`), the 7th `DialogueOverlay` constructor argument, alongside the existing `onTeach` one.
- [ ] **Open item, confirmed still out of scope on pickup**: an actual Bulletin Board entity/interactable — this milestone's own doc named it explicitly optional, and NPC dialogue (this milestone's actual default-scope ask) is a complete, real quest-giving surface on its own; building a second one wasn't requested when this doc was picked up. Left here, not silently dropped, as the one remaining open item if a future milestone wants a second quest-giving surface.

## Architecture notes / non-goals

See [EPIC-31](../stories/EPIC-31-world-hud-progression-overhaul.md)'s epic-wide non-goals — confirmed upheld: `IrlQuestSystem.ts` was not touched at all (verified by `git diff` scope), and stays a separate self-attested daily-buff mechanic alongside the new location-verified one. No multiplayer-shared quest state — `worldQuests` is plain local `GameState`, same persistence path as everything else. `WorldQuest` targets are zone-id (`WorldZoneId`, the literal strings `WorldScene.updateZone()` itself produces) and npc-id/commons-key driven, never a skin-specific asset name, per `CLAUDE.md`'s Critical Architecture Rule.
